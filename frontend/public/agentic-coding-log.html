The thesis, in one line: AI is unreasonably good at scaffolding CRUD, dashboards, and repetitive React components. It is unreliable on business rules, domain safety guarantees, deterministic hashing, and framework quirks like Express route ordering. The 20% that is human is the 20% that would have shipped bugs.

2. The six caught-bad-AI cases

Each case shows what the AI produced, why a human pushed back, and what shipped. Diffs are trimmed to the essentials.

caught bad ai Case 1: An AI-drafted validation rule that would have flagged every subprime loan

Module
validation-engine
Prompt used
rule_from_nl "flag loans where interest rate looks unusual"
Surface
/admin/rules dry-run preview
Severity if shipped
high would have generated ~40% false positives on a real subprime tape
What the AI proposed
{
  "ruleId": "SUBPRIME_INTEREST",
  "name":   "Unusually high interest rate",
  "severity": "blocking",
  "expression": { "op": "gt", "field": "interestRate", "value": 15 }
}
Human review notes
"Subprime auto and consumer loans routinely price at 15–25%. This would fire on every legitimately subprime pool the tool is supposed to serve. The problem statement itself says the valid range is 0–30. 'Blocking' severity is also wrong — an out-of-range rate is a data-quality flag, not a hard reject."
What shipped
{
  "ruleId":  "INTEREST_RATE_OUT_OF_RANGE",
  "name":    "Interest rate outside 0–30% band",
  "severity": "medium",
  "messageTemplate": "interestRate {value} outside 0–30 band",
  "expression": {
    "op": "or",
    "of": [
      { "op": "lt", "field": "interestRate", "value": 0 },
      { "op": "gt", "field": "interestRate", "value": 30 }
    ]
  }
}

Lives in samples/validation_rules.json and the caught_bad_ai seed entry in seedDevLog.js.

caught bad ai Case 2: accept_ai mutated the canonical Loan directly, bypassing the whitelist

Module
ai-service
Prompt used
"implement PATCH /api/exceptions/:id/resolve for action=accept_ai"
Severity if shipped
critical the AI could have set verificationStatus or written arbitrary Mongo paths
What the AI produced
// PATCH /api/exceptions/:id/resolve — accept_ai branch (AI draft)
const aiRec = await AiRecommendation.findById(body.aiRecommendationId);
const loan  = await Loan.findOne({ loanId: exception.loanId });

// Just apply everything the AI suggested. What could go wrong?
Object.assign(loan, aiRec.output.suggestedFields);
await loan.save();
Human review notes
"This is the single most dangerous line in the codebase. AI must never mark a loan verified — Object.assign against untrusted AI output means any key the model returns lands on the record, including verificationStatus. This has to go through a hard-coded whitelist and drop everything else."
What shipped
const WHITELIST = new Set([
  "borrowerName","state","currentBalance","interestRate",
  "paymentStatus","daysPastDue","lastUpdatedAt","documentStatus",
]);

const beforeValues = {}, afterValues = {}, droppedFields = [];
for (const [k, v] of Object.entries(aiRec.output.suggestedFields || {})) {
  if (!WHITELIST.has(k)) { droppedFields.push(k); continue; }
  beforeValues[k] = loan[k];
  loan[k] = v;
  afterValues[k] = v;
}
await loan.save();

await ReviewDecision.create({
  loanId, exceptionId, action: "accept_ai",
  beforeValues, afterValues,
  aiRecommendationId: aiRec._id, reviewer: req.user.id,
  notes: droppedFields.length ? { droppedFields } : undefined,
});

Enforcement lives in backend/src/routes/exceptions.js — same whitelist as PATCH /api/loans/:loanId, no exceptions.

caught bad ai Case 3: canonicalStringify mangled ObjectIds → bundle hash always mismatched

Module
verified-record / hash chain
Prompt used
"write a deterministic JSON stringifier for the audit chain hash"
Symptom
Client-side bundleHash re-verification always returned MISMATCH, even on unmodified bundles
Severity if shipped
medium the export bundle's integrity claim would have been false
What the AI produced
function sortValue(value) {
  if (value === null || value === undefined) return value;
  if (Array.isArray(value)) return value.map(sortValue);
  if (value instanceof Date) return value.toISOString();
  if (typeof value === "object") {
    const out = {};
    for (const key of Object.keys(value).sort()) {
      const v = value[key];
      if (v === undefined) continue;
      out[key] = sortValue(v);   // ← recurses into ObjectId internals
    }
    return out;
  }
  return value;
}
Human review notes
"The client reads the bundle as pure JSON, so every ObjectId is already a hex string on that side. The server's sortValue sees a Mongoose ObjectId — an object — and recurses into {_bsontype, id: Buffer}. Two different canonical forms, two different hashes. Ship this and every 'verify the bundle' claim in the demo is a lie."
What shipped
function sortValue(value) {
  if (value === null || value === undefined) return value;
  if (Array.isArray(value)) return value.map(sortValue);
  if (value instanceof Date) return value.toISOString();
  if (typeof value === "object") {
    // ObjectId, Buffer, Decimal128 all expose toJSON — respect it so the
    // canonical form matches what JSON.stringify produces on the wire.
    if (typeof value.toJSON === "function") return sortValue(value.toJSON());
    const out = {};
    for (const key of Object.keys(value).sort()) {
      const v = value[key];
      if (v === undefined) continue;
      out[key] = sortValue(v);
    }
    return out;
  }
  return value;
}

Lives in backend/src/utils/hash.js. Smoke test now verifies client re-hash against server hash — MATCH.

caught bad ai Case 4: Express route ordering — /chain-check matched /:loanId and rejected consumers

Module
consumer-portal
Prompt used
"add POST /api/verified/chain-check that takes {loanIds:[...]}"
Symptom
Consumer login → verified records page → console: Role 'consumer' is not permitted
Severity if shipped
medium the entire consumer chain-integrity feature would have been non-functional
What the AI produced
router.use(requireAuth);

router.post("/:loanId",         requireRole("reviewer","admin"), verifyHandler);
router.post("/:loanId/unverify", requireRole("admin"),           unverifyHandler);
router.get ("/",                                                 listVerifiedHandler);

// Added at the bottom — feels natural because it's a "utility" route.
router.post("/chain-check",                                       batchChainHandler);
Human review notes
"Express matches routes in declaration order. router.post('/:loanId', requireRole('reviewer','admin')) runs first, matches /chain-check as a loanId, and 403s the consumer. The AI has no mental model of Express matching. Static-path routes must come before parameterised ones."
What shipped
router.use(requireAuth);

// Static-path POSTs must be registered BEFORE `/:loanId` so Express doesn't
// route `/chain-check` into the reviewer-only verify handler.
router.post("/chain-check", batchChainHandler);

router.post("/:loanId",          requireRole("reviewer","admin"), verifyHandler);
router.post("/:loanId/unverify", requireRole("admin"),           unverifyHandler);

Same fix category applied later for /export and /export/bundle vs /:loanId. In backend/src/routes/verified.js.

caught bad ai Case 5: Number(null) === 0 silently broke every Converse query

Module
ai-service / converse
Prompt used
"parse the AI's suggested limit for the Mongo query, cap at 50"
Symptom
Every fallback Converse query returned 500 the limit must be positive
Severity if shipped
medium the whole 4.5 differentiator would have been broken in fallback mode
What the AI produced
const limit = Number.isFinite(Number(out.limit))
  ? Math.min(50, Number(out.limit))
  : 50;
Human review notes
"When the fallback parser has no 'top N' intent, out.limit is null. Number(null) === 0. Number.isFinite(0) === true. So limit = Math.min(50, 0) = 0. Mongo throws. The AI wrote a 'finite' check that treats 0 as valid, which is exactly the case we need to reject."
What shipped
const rawLimit = Number(out.limit);
const limit = Number.isFinite(rawLimit) && rawLimit > 0
  ? Math.min(50, rawLimit)
  : 50;

Lives in backend/src/routes/converse.js. All four seeded Converse example chips now return results in fallback mode.

caught bad ai Case 6: PATCH /rules/:id/reject skipped auto-dismiss for AI-drafted rules

Module
validation-engine / admin
Prompt used
"when an admin rejects a rule, re-run validation so open exceptions get auto-dismissed"
Symptom
Reject an approved AI rule → its open exceptions stay open in the reviewer queue
Severity if shipped
medium orphaned exceptions in the queue, confusing the reviewer workflow
What the AI produced
// Deactivation → re-run validation so the engine's auto-dismiss sweep fires.
// AI's reasoning: "AI rules aren't 'real' rules, no need to re-sweep."
let runResult = null;
if (rule.origin !== "ai_generated") {
  runResult = await runValidationForLoans(null, ctx);
}
Human review notes
"The AI is inventing a distinction that doesn't exist in the domain. A rule that fired and created 12 real Exception rows is 100% a real rule, regardless of who drafted it. Rejecting it must always sweep. This branch would have left ghost exceptions in the queue every time we demoed the admin flow."
What shipped
// Deactivation always triggers a full re-run so the engine's sweep can
// auto-dismiss any remaining open exceptions owned by this rule.
const runResult = await runValidationForLoans(null, {
  actor: req.user.id,
  actorRole: req.user.role,
});

Verified by a two-step smoke: create → approve → confirm openCount=1, then reject → confirm openCount=0. In backend/src/routes/rules.js.

4. Human review process

Per-module checkpoint

Each module was built with a written acceptance criterion attached. Before moving to the next module, the developer ran the acceptance checks manually against the running app or via curl. Anything that failed was fixed before proceeding — which is why the smoke test lands at 39 of 39 assertions green today.

Standing rules for every AI diff

  • No Object.assign against AI output. Every AI-suggested field mutation goes through a hard-coded whitelist (see Case 2).
  • Every AI recommendation persisted before any mutation. If the reviewer never explicitly accepted a suggestion, the canonical Loan cannot have moved.
  • No new npm dependencies without a written justification. The whole app has 0 chart libraries, 0 crypto libraries, 0 CSV libraries beyond csv-parse. Everything else is Node built-ins.
  • ASCII-only logs. Windows cp1252 fallback would crash our reset banner otherwise.
  • Every audit-event write goes through appendAuditEvent. Even where insertMany would be faster. Correctness > throughput for demo integrity.

Automated tests that back the manual review

npm run smoke
14-step end-to-end pipeline — 39 assertions, exits with fail count. Runs against a scratch DB so it can't touch the demo state.
trust:test
In-memory trust-score assertions (5 synthetic loans) — pins the formula before UI changes ship.
chain:verify
Walks every loan's audit chain in the current DB. Runs before every demo rehearsal.
demo:tamper / untamper
Reproducible chain-break test — used both as a demo prop and as a manual regression before every stage rehearsal.
